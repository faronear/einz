# Einz 账号体系设计（与现有架构的结合）— `[待评审]`

2026-10-19 初稿。目标：为将来 App Store 上架付费化（订阅/买断）预留「判定谁买过」的身份基座，同时**不破坏 Einz 的隐私核心**——服务器不见明文、端到端加密、无强身份绑定。本文档只做设计评审，未实现。

## 一、为什么 Einz 需要账号（以及为什么以前不需要）

现有架构的授权单位是**通道（entrance）**：每台安装生成密钥对，服务端只认公钥挑战签名（auth.ts），`install_uid` 只是设备级关联标记（installUid.ts 明文警告：不要拿它做授权）。这个模型对「自用/熟人组空间」是完美的，但三件事它做不到：

1. **付费权益归属**：订阅跟着 Apple ID 走，但你需要一个服务端可验证的「这个人买过」判定——通道可以随时重建（卸载重装、清数据），权益必须落在比通道更持久的实体上；
2. **跨设备/跨空间权益共享**：一个用户可能有多条通道（多设备、多个空间），买一次应处处生效；
3. **账号恢复/找回**：现在丢设备 = 丢数据（by design），付费用户会期待至少「权益」可以找回。

## 二、设计原则（老板核心约束的推论）

1. **账号是权益层，不是数据层**。秘境数据仍然只住在端到端加密的通道里，账号系统**碰不到 Space Key**——账号被黑/被封，损失的是订阅权益，不是聊天记录。这是与微信式账号体系的本质区别，必须写进产品文案。
2. **账号可选**。不登录账号一切照旧（现有通道模型完整可用）；只有付费权益需要账号。免费用户永远不被迫注册。
3. **最小身份**。账号只收：登录凭证（Sign in with Apple 或邮箱）+ 收据/交易信息 + 订阅状态。不收手机号、不收通讯录、不画像。
4. **服务器为唯一真相源**（沿用 escrow 口令的既有原则）：权益判定在服务端做，客户端只缓存展示。

## 三、账号模型

### 3.1 实体

```
accounts            账号（权益归属单位）
  account_uid       服务端生成的随机 ID（不基于 PII 派生）
  apple_sub         Sign in with Apple 的 stable user identifier（走 Apple 登录时）
  email             走 magic-link 邮箱登录时（与 notify_emails 的规范化同规则）
  created_at

account_entrances   账号 ↔ 通道绑定（一个账号可绑多条通道 = 多设备/多空间）
  account_uid
  entrance_id       现有 entrances 表的键
  bound_at
  UNIQUE(entrance_id)   -- 一条通道同时只归一个账号（换绑=先解绑）

purchases           交易（服务端从 App Store Server API 拉取/验证）
  transaction_id    Apple 唯一交易号（PRIMARY KEY，幂等）
  account_uid
  product_id        订阅档位/买断商品
  status            active / expired / refunded
  expires_at        订阅续期时间（买断为 NULL）
  original_tx_id    订阅续期链的根交易（判首购 vs 续费）
```

### 3.2 登录方式（两选一，都做）

| 方式                   | 适用                 | 说明                                                                                                                                                                    |
| ---------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Sign in with Apple** | iOS/macOS 主路径     | 上架 App Store 后，若提供第三方登录则 Apple 强制要求 SiwA 也在选项里——干脆主推它。拿到 stable user id（对开发者不可变的 `sub`），隐私好（可隐藏真实邮箱），无需密码管理 |
| **Magic link 邮箱**    | 非 Apple 平台 + 备用 | 复用现有 mailer/SMTP 基建（notifier.ts 那套出站已验证过 Oracle SMTP 可用）；邮件里带一次性 token，点击即登录。账号注册与邮件通知共用同一邮箱规范化规则                  |

不做的：密码登录（要管哈希、找回、撞库——成本高收益低）、手机号（违背最小身份）、第三方 OAuth（Google 等，上架后再议）。

### 3.3 通道绑定（账号体系与 Einz 现状的「接合点」）

这是整个设计里唯一动现有协议的地方：

- App 登录账号后，把当前通道的 `entrance_id` 报给服务端：`POST /account/bind`（带通道签名鉴权，复用现有 auth）；
- 服务端校验该通道存在且签名有效 → 写 `account_entrances`；
- **权益判定 = 查通道所在账号的有效订阅**：`GET /entitlements`（通道签名鉴权）→ 服务端 `entrances → account_entrances → purchases(status=active)`，返回 `{ paid: bool, plan, expiresAt }`；
- 一条通道换绑到新账号：显性操作 + 老账号解绑，防「借通道转移权益」套利（同一时刻只归一个账号已保证）。

**不绑定的兼容性**：未绑定账号的通道查权益永远 `paid: false`——付费化上线前的存量用户不受任何影响。

## 四、付费化落地路径（结合 §付费模式讨论）

1. **阶段 0（现在，免费期）**：只做账号基建——登录 + 绑定 + `GET /entitlements` 恒 `paid:true`（或干脆不查）。App 侧把登录入口藏在设置里，可完全跳过。
2. **阶段 1（上架时）**：App Store Connect 配订阅商品（建议：月订阅 + 年订阅 + 永久买断三档）；客户端 StoreKit 2 拉商品、发起购买；购买成功后把交易凭证发服务端 `POST /purchases/verify` → 服务端调 **App Store Server API** 验签落 `purchases` → 权益即生效。
3. **阶段 2（付费墙启用）**：客户端按 `/entitlements` 显付费墙。策略：**已装存量用户赠终身免费**（服务端按「绑定时间早于 cutoff」判定，账号体系让这个判定可跨设备）——这是「先免费过一段时间后付费」的平滑实现。
4. 订阅生命周期事件（续期/退款/家组）走 **App Store Server Notifications V2** webhook 到服务端，自动同步 `purchases.status`。

## 六、风险与边界（评审重点）

1. **权益找回 vs 隐私的张力**： magic-link 邮箱登录意味着服务器存了一个「邮箱 ↔ 账号 ↔ 通道列表」的关联。Einz 服务端现在只知道「匿名通道」，账号体系会让服务器知道「这个邮箱在这些空间里有通道」。**建议**：绑定关系只存 entrance_id（已是随机 ID），服务器仍然不知道空间里的人是谁、说了什么——这是可接受的最小暴露。评审时老板确认这条可接受再继续。
2. **SiwA 的 `sub` 稳定性**：Apple 的 user identifier 对同一开发者账号稳定，但用户可选择「隐藏邮箱」产生 relay 邮箱——magic link 和 SiwA 两路径可能得到同一真人两个账号。缓解：以 SiwA sub 为主键、允许账号合并（后续再说，v1 不做）。
3. **家组共享（Family Sharing）**：订阅支持家组会让权益判定复杂（服务端要查家组交易）。v1 建议不开家组，评审时定。
4. **退款薅羊毛**：ASNSv2 的 `REFUND` 事件要同步撤销权益；买断制尤其要处理（订阅自然到期兜底）。
5. **中国大陆区**：ICP 备案前置；且大陆区对 IAP 之外的解锁无灰度空间，全部走 IAP。
6. **不做的事**：账号体系不做「聊天数据云端备份」（那是另一个大工程，见 productLens 预留的模型 B）；不做社交关系；不给 CLI 增加登录阻断。

## 七、评审问题（需要老板拍板）

1. 登录主路径 SiwA + magic link 备用，可以吗？还是只要一种？
2. §六.1 的「邮箱 ↔ 通道列表」最小暴露，你能接受吗？（这是账号体系唯一刺破匿名性的地方）
3. 免费期存量用户「赠终身免费」还是「赠 N 年」？cutoff 定在付费墙启用日？
4. 订阅档位/定价先不定，但买断制要不要保留？（IAP 买断 + 订阅并存是允许的）
