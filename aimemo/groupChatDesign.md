# 多人群聊（一期）设计方案 —— 2026-10-03 评估

> **2026-10-04 重大修订：取消升格。** 老板拍板"一旦定了双人，就永远不变"——空间类型
> 在**创建时选定**（向导第 2 步：双人秘境 / 群组秘境），之后不可更改，也不存在
> "两人空间后来变成群"。原方案 C（duo 满员后签发 invite 自动升格 group）整套作废：
> 随之删掉了 `maybeUpgradeToGroup`、`UPGRADE_NOT_ALLOWED`、签发/join 双闸门、
> `space.upgraded` 帧、升格确认弹窗，以及"升格时在聊天流落系统消息"这条需求
>（没有升格就没有"另一方不知情"）。代价：duo 想加人只能另建群组空间，**历史消息
> 留在旧空间**（新空间 = 新 Space Key）。下文凡涉及"自动升格/方案 C"的段落均以
> 本修订为准。

老板已拍板的方向性决策：

| 决策点           | 结论                                                      |
| ---------------- | --------------------------------------------------------- |
| 群规模上限       | 3-4 人小群（服务端可设上限常量 `maxMembersPerSpace`，UI 不做通用人海列表）|
| 新成员历史可见性 | 可见全部历史（与现有 Space Key 模型一致，产品上明示即可） |
| 群语音通话       | 一期禁用，call.\* 信令仅限两人私聊空间                    |
| 成员管理权限     | 全员平等：所有人可邀请；**不做踢人**                      |
| 空间类型（2026-10-04 修订） | **创建时选定，永不改变**：duo=严格二人（上限恒 2、可通话）；group=群空间（上限 `maxMembersPerSpace`、禁通话）。**没有升格**——duo 想加人只能另建群组空间（历史留在旧空间） |
| 创建/加入流程    | 类型由创建者在向导第 2 步选（关于我 → **类型** → 口令 → PIN）；duo/group **共享同一套创建与加入流程**（mode 仅服务端生效 + 少量 UI 文案/入口差异）；创建时不预置对方，partner 加入时自己填名 |
| 加通道 token     | 邀请链接分两种（2026-10-04 收敛为 **invite / attach**）：invite 开新身份；attach 进已有身份（指向自己=换设备，指向别人=**帮对方找回**） |
| 丢设备 / 换设备（2026-10-04 补） | **永远能回来**，只要空间里还有任一安装存在。duo 满 2 人签不出 invite，但 attach 指向对方**永远可用**（要共享口令授权）；她回来仍在自己的身份上（历史/配色/别人的认知都对得上）。**签发与使用该链接绝不撤销对方现有通道**——没丢设备、只想再挂一台也用它（老板 2026-10-04 明确要求） |
| 邀请 token 策略  | 维持**一次性**（现状）：每个新成员单独生成一条邀请链接    |
| 成员退出         | **一期不考虑退出**——入群即永不退群（2026-10-03 拍板）     |
| 老客户端兼容     | **不做**——现仅少量测试用户，一次性全员升级，协议无双接受（2026-10-03 拍板） |

## 现状结论（已核实代码）

服务端消息层天然接近多人模型，改动集中在上层：

- `space_members` 按 (space_id, slot) 组织，member_id 是身份锚点，一人多 entrance 共享
- messages 按 (space_id, server_sequence) 编号；WS 广播带 member_id 供客户端二次过滤
- receipts 按 (space, member) 记水位，天然支持 N 人
- E2EE 为单一对称 Space Key，N 人共享即用，**密码层一期零改动**

真正锁死"两人"的三层：slot 0/1 二槽语义（服务端）、`peerName/peerGender` 二元创建协议（shared）、`chat_page.dart` 的"一个对方"假设（app）。

## 改动清单

### 服务端（~2-3 天）

- spaces 表加 `mode` 字段（`duo` | `group`，NOT NULL 默认 'duo'；存量空间回填 'duo'
  → 现存情侣空间天然是严格二人空间，零迁移成本）：duo = 二人私密空间（上限 2、
  通话可用），group = 多人群空间（上限 maxMembersPerSpace、通话禁用）
- **创建时选定类型**（2026-10-04 修订；向导第 2 步：关于我 → **类型** → 口令 → PIN）：
  create 带 `mode`（`duo` 缺省 | `group`），**落库后永不 UPDATE**——没有状态机、
  没有单向往返。创建流程仍然零打扰：只填创建者自己的名字，**不预置伴侣**，
  partner 在新成员加入流里自己填名（create 已删 peer_name/peer_gender）
- slot 0/1 → 开放为小整数槽位（保留 UNIQUE(space_id, slot)）；join 的 slot 参数改为
  显式语义（无老客户端兼容）：**不带 slot = 新身份**（分配最小空 slot、生成新
  member_id），**带 slot = 已有成员加通道**（slot 必须已有人，否则报错）
- join_tokens 加 `purpose` 字段（**发起人生成时选定**）：
  invite = 邀请新成员（新身份）；另一个值 = 绑定发起人自己的 slot（由
  created_by_entrance → member → slot 查出），仅该成员可在新设备加通道——
  彻底消除"任何成员任选他人身份加通道"的冒充面（现状身份选择页允许选任意人）
  > **2026-10-04 改名**：那个值当时叫 `channel`，现已改名 **`attach`** 并扩展为
  > "进**已有身份**"（target 指向别人 = 帮对方找回）。原因：① 要覆盖"帮别人找回"，
  > channel（通道）对那个场景不成立；② `docs/GLOSSARY.md` 明确"英文不用 channel"。
  > 下文沿用当时的 `channel` 字样，读作 `attach`。
- join 校验：purpose=invite → 必须不带 slot（新身份，分配最小空槽）；purpose=channel
  → 必须带 slot 且 == 发起人 slot（不符 403）；原"任选已有身份"路径删除
- 人数上限两道互不干扰的闸（2026-10-04 修订）：**duo 恒 2**（第 3 个身份一律
  `DUO_FULL` 409——双人秘境不是"配置限制"，是定义；且 duo 满 2 人时**签不出
  invite**，当场拒），**group 看 `maxMembersPerSpace`**（serverConfig.json，
  建议默认 4，与 maxSpaces / maxEntrancesPerSpace 同一模式，不写死代码常量）超限
  → 409 `SPACE_FULL`。计数只算 active 身份（同身份多通道不重复），且在事务内计
- **定向 token（2026-10-04）**：join_tokens 加 `target_member_id`——attach 指向
  谁就进谁的身份。指向**别人**时路由层校验共享口令（与"撤销别人通道"同档，
  见 docs/SECURITY.md）；preflight 回带 `targetName`/`targetIsIssuer`，向导据此
  显示「把「X」的身份接到这台设备上」并跳过填名字。
  **不做任何撤销**：join 路径只新增一条通道（`revoked` 只有"显式撤销别人"与
  "自助退役"两处会写），回归测试见 server/test/join_token_target.test.ts
- preflight 返回 purpose + 受邀人（token 签发者）名字 + 成员数：invite token →
  客户端走"新成员加入"流（填自己名字，无身份选择页）；channel token → 客户端走
  "在其他设备加入我的账号"流（身份由链接绑定，无选择）；token 逐人一次性
  （现状一次性 / 24h 机制不变，不新增吊销端点）
- **duo 与 group 共享同一套创建/加入流程与代码路径**（不出现按 mode 分叉的流程
  分支）：mode 只在服务端生效（人数上限、call.\* 判定）+ 少量 UI 文案/入口差异
  （duo「邀请伴侣」、满员隐藏邀请入口、隐藏通话入口）；客户端不按 mode 画两套向导
- WS 加 `member.joined` 广播（**仅新身份**入网时发——自己加通道不发，否则别人会
  以为来了新人）；**无 member.left**（一期无退出）。**没有 `space.upgraded`**
  （2026-10-04：取消升格后不需要；随之也不需要"本地系统消息"设施）
- notifier.ts（948 行）核对：未读口径已是 member 维度（`!= 自己身份`），基本不用动；
  ① 重提封顶是**按收件人邮箱**计的，与"对方"无关——核对后不动；② `sendPushHint`
  排除的是 entrance 维度（push.ts），同身份其他通道也会收到推送 → 改为按 member 排除；
  ③ 邮件「对方」回退文案改群口径
- call.\* 信令改按 **mode** 判定：duo 空间可用（二人私聊通话），group 空间直接拒绝
  （服务端兜底 + 客户端隐藏入口；group 即使只有 2 个人也不通话——**类型一选定，
  通话能力就定了**）
- key_escrow 口令归属：一期维持"创建者口令"不变，新成员用同一口令取钥，文档注明

## 分期

- **一期（2-3 周）**：上述全部；**创建时选定类型**（双人 / 群组，之后不可改；
  group 禁通话；duo 恒 2 人）；创建流程不预置对方，新成员自己填名；
  邀请链接双 purpose（invite/channel，channel 绑定发起人身份）；新成员可见全部历史
  （加入页明示文案）；token 逐人一次性；成员无退出；一次性升级（v3，服务端先行）
- **二期候选**：成员退出（含状态机/重入/广播，依赖下条）、密钥按成员封装（退群作废）、
  踢人+密钥轮换、群通话（Mesh ≤4 人）、CLI 深度适配（含创建/加入群空间入口）、
  ~~"启动时强制升级"~~ ✅ **2026-10-04 已实现**（`/health` 加 `min_app_version` +
  `app_download_url`；App 首屏核对，低于下限弹不可关闭的升级窗，见
  `app/lib/widgets/version_gate.dart`、`docs/DEPLOYMENT.md` §2.2、`docs/PROTOCOL_MULTIVERSE.md` §4.1）
