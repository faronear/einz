## 1. 一句话结论

**各端本地转写、结果只存本地**：录音消息照常 E2EE 收发；每台设备拿到**本机解密后的音频**后，
用端侧离线 ASR（`sherpa-onnx`）**自动转写**，文本写进一张**本地派生表**，渲染在录音气泡下方。
**不改协议、不改服务端、不碰 E2EE 密文**。转写结果随模型升级可重算/回填。

---

## 2. 需求与已拍板决策（老板 2026-10-09）

| # | 议题 | 结论 |
| - | ---- | ---- |
| 1 | 转写发生在哪端 | **各端各自本地转写**（发送端转自己的，接收端转对方发来的） |
| 2 | 触发方式 | **自动**——收到（且音频已解密）即转。数量少、几乎每条都会被看，索性全转 |
| 3 | 转写结果归属 | **本地派生数据**，**不上传、不进密文、不参与同步** |
| 4 | 为什么不让发送端转好写进消息 | 转写**可能不准**，且**未来模型升级**会有更好结果；固化进服务端密文就再也改不了 |
| 5 | 服务器角色 | **零改动**，继续只搬密文 |

### 2.1 为什么是「派生数据」视角

转写文本 = `f(音频, 模型)`，与「视频首帧缩略图 = `f(视频)`」同性质：**不是作者内容，是可重算的派生数据**。
派生数据就该存本地、可丢弃、可重算，而不是当成不可变事实写进 E2EE 密文。由此带来三个好处：

- **E2EE 承诺不动**（服务器看不见任何东西）；
- **模型升级可回填**：换更强的模型后对历史语音重转即可，无需任何同步；
- **换机也稳**：新设备从服务器拉回密文音频、解密后自己重算，不依赖旧设备。

## 3. 为什么不选其他方案

| 方案 | 否决理由 |
| ---- | -------- |
| 发送端转写、并入消息密文 | 把旧模型的错误结果**永久固化**在服务端密文里，模型升级无法改进 |
| 云端 ASR（讯飞/阿里/OpenAI） | 要上传**明文音频**，直接违背 E2EE |
| 系统原生 API（`SFSpeechRecognizer` / Android `SpeechRecognizer`） | iOS 中文离线模型要联网下载；Android 依赖 Google 服务，国产机基本不可用；Flutter 插件多为**麦克风流式**设计，不适配「转写已有音频文件」 |
| 真·消息编辑（更新已有 messageId） | 现有消息**不可变**（`LocalMessages` 以 `messageId` 为主键、无编辑字段；协议无编辑帧），要动 wire + 服务端 + 回执/焚毁/序列对齐，代价过大 |
| 「先发音频、后台转写、再补文字合并」 | 系统不会自动合并两条消息；构造合并机制复杂，且同样会固化旧结果 |

## 4. 技术选型

- **引擎**：`sherpa-onnx`（k2-fsa，Apache-2.0）。官方 Flutter 包 `sherpa_onnx`（FFI），
  同时覆盖 iOS / Android；非流式离线识别。
- **前端处理**：可选 Silero VAD 切掉录音两端的静音，提升准确率、缩短耗时。
- **音频格式**：ASR 需要 **16 kHz 单声道 PCM**。语音消息时长上限 **60s**（`chat_page.dart`），
  当前 `record` 录的是 m4a/AAC，**必须先解决格式问题**（见 §8）。

## 5. 模型选型（SenseVoice vs Paraformer）

| 维度 | SenseVoice-Small | Paraformer-zh-small |
| ---- | ---------------- | ------------------- |
| int8 体积 | **≈ 230 MB** | **79 MB** |
| 语言 | zh / 粤 / en / ja / ko | 中 + 英（含河南/天津/四川口音） |
| 口语 / 方言 | **更稳**（训练数据多样、含口语与多方言） | 标准普通话强，非正式场景下降 |
| 中英混说 | **支持好** | 一般（超出中英即掉） |
| 标点 | **自带标点 + ITN**（数字规整） | 待核实：sherpa-onnx 版常需**另配标点模型**（CT-Transformer，约几十 MB） |
| 速度 | 快 | **更快** |
| 额外输出 | 带情感/事件标签，需**剥离**后展示 | 纯净文本 |
| 许可 | Apache-2.0（**模型许可需再核**） | Apache-2.0 |

**结论：默认选 SenseVoice-Small**（老板 2026-10-09 定）——**先按它落地**，Phase 0 用真实语音 A/B 后最终确认。
理由（按重要性）：

1. **标点基本是决定性的**：气泡下挂一行转写文字，有无标点直接决定可读性。SenseVoice 一个自包含模型
   直接出带标点的句子；Paraformer 在 sherpa-onnx 里通常要再配一个标点模型（CT-Transformer），
   省下的体积与复杂度又被吃回去（此点标"待核实"，Phase 0 确认 Paraformer 原生输出是否带标点）。
2. 本产品内容是**情侣/熟人日常口语**，SenseVoice 训练数据更偏口语/多方言，更贴场景；
   Paraformer 在正式标准普通话上更准，但本产品用不到那个优势。
3. **中英混说**在日常聊天里很常见，SenseVoice 明显更稳。
4. 体积不是主要顾虑：只有两台自用设备、又是侧载，230 MB 打包进产物可接受（不进 git，build 时脚本拉取）。
   且 §2.1 的「可换模型 + 可重算」意味着**这不是锁定**——真机效果不满意，换 Paraformer 重转即可，零迁移成本。

**降级条件**：若 Phase 0 真机实测「Paraformer-zh-small 的口语识别 + 标点」在实际语音上够用，
则改用 `Paraformer-zh-small`（79 MB、更快）作为移动端更省的方案。

> Phase 0 复核：用**老板的真实语音**对两模型各跑一遍，比较「口语短句 / 中英混说 / 标点」三项，据此最终定。

## 6. 架构与数据流

```text
发送端：按住录音 ─► 本地明文音频文件 ─►（加密上传，流程不变）
                                      └─► 后台 isolate: ASR ─► 本地转写表 ─► 气泡下方显示文字

接收端：收到消息 ─► 下载密文附件 ─► 解密为本地明文 ─► 后台 isolate: ASR ─► 本地转写表 ─► 显示
```

- 两端**各自独立**转写，互不通信；转写文本**不产生任何网络流量**。
- 转写在**后台 isolate** 串行执行，避免抢 UI 线程、避免并发抢 CPU。

## 7. 数据模型

新增 drift 表 `LocalVoiceTranscripts`（**升一版 schema**）：

| 列 | 说明 |
| -- | ---- |
| `messageId` | 主键，外键 → `LocalMessages(messageId)`，**级联删除** |
| `text` | 转写结果 |
| `modelId` | 模型标识（如 `sense-voice-small`） |
| `modelVersion` | 模型版本/文件哈希——**判断是否需要重转的开关** |
| `audioSha256` | 音频密文 sha256——音频若变化则转写失效 |
| `language` | 识别到的语言（SenseVoice 会返回） |
| `status` | `pending` / `done` / `failed` / `stale` / `unavailable` |
| `updatedAt` | 时间戳 |

**关键约束**：

- 该表**纯本地**，不进 E2EE 密文、不参与同步、**服务端不可见**。
- **随消息级联删除**：音频被阅后即焚或删除时，转写必须同时消失。
- **备份按"可丢弃缓存"处理**：能从密文音频重算，不写进备份快照（避免把可能不准的文字带进备份）。
- `modelVersion` 或 `audioSha256` 变化 → 标记 `stale`，可重转。

## 8. 音频格式问题（必须解决）

ASR 输入需 16 kHz 单声道 PCM，现有录音是 m4a/AAC。三条路：

1. **【推荐】语音消息改存 16kHz 单声道 WAV**（`record` 可直接出 wav）：ASR 零转换、无额外依赖；
   代价是体积约 8×（60s ≈ 1.9 MB，个人自用可接受）。旧消息维持原样、不强制转写。
2. 保留 m4a，转写前**解码为 PCM**：需引入解码能力（`ffmpeg` 类库体积大且在维护上有风险，
   或走平台原生 `MediaCodec` / `AVAudioConverter` 平台通道，工作量大）。
3. 录音同时**旁路录一份 wav** 仅用于 ASR：改动录音链路，双写文件。

倾向 **1**；Phase 0 一并验证音量/音质与体积是否可接受。

## 9. 触发与调度

- 收到消息且**音频已解密**（附件 `status=downloaded` 或本机即发送端）→ 入本地转写队列。
- 队列在**后台 isolate 串行消费**；失败重试上限（建议 2 次）后置 `failed`。
- 模型未就绪（未打包/未下载）→ 置 `unavailable`，UI 不露破绽（见 §10），提供手动入口。
- **不做**"升级后全量批量重转"：CPU 密集。倾向**惰性重转**（进入会话/展开该条时才重算）或显式按钮。

## 10. UI

- 气泡：现有**波形 + 秒数**保留，**下方加一行转写文字**。
- 转写中：占位（骨架/「转写中…」）。
- 失败 / 未就绪：显示可点的**手动转写**入口，不显示错误堆栈。
- `stale`：显示「可重新转写」入口。
- 注：转写可能不准，**不提供编辑**（本期）；如未来要允许用户改文字，则性质从"缓存"变为
  "用户内容"，需重新讨论存储与备份策略。

## 13. 风险

1. **原生插件构建（最高）**：`sherpa_onnx` 是重 FFI 原生插件，放大 Codemagic 与本机构建不确定性。
   **Phase 0 必须先行。**
2. **音频格式**：m4a→PCM 的解码链路是隐藏工作量，见 §8。
3. **模型体积/分发**：230 MB 的打包或下载都要处理。
4. **两端结果不一致**：D 方案固有属性（各自模型/版本可能不同），需接受。
5. **耗电/发热**：自动全员转写 + 两端各算一次；靠后台 isolate 串行 + 队列限流缓解。
6. **标点**：取决于模型；Paraformer 路径可能需额外标点模型。
7. **验证成本落在老板身上**：ASR 效果只能真机自测，我这边只跑 `flutter analyze`。
