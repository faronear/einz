## 1. 一句话结论

**各端本地转写、结果只存本地**：录音消息照常 E2EE 收发；每台设备拿到**本机解密后的音频**后，
用端侧离线 ASR（`sherpa-onnx`）**自动转写**，文本写进一张**本地派生表**，渲染在录音气泡下方。
**不改协议、不改服务端、不碰 E2EE 密文**。转写结果随模型升级可重算/回填。

## 2. 需求与已拍板决策（老板 2026-10-09）

| # | 议题 | 结论 |
| - | ---- | ---- |
| 1 | 转写发生在哪端 | **各端各自本地转写**（发送端转自己的，接收端转对方发来的） |
| 2 | 触发方式 | **自动**——收到（且音频已解密）即转。数量少、几乎每条都会被看，索性全转 |
| 3 | 转写结果归属 | **本地派生数据**，**不上传、不进密文、不参与同步** |
| 4 | 为什么不让发送端转好写进消息 | 转写**可能不准**，且**未来模型升级**会有更好结果；固化进服务端密文就再也改不了 |
| 5 | 服务器角色 | **零改动**，继续只搬密文 |

### 2.1 为什么是「派生数据」视角

转写文本 = `f(音频, 模型)`，与「视频首帧缩略图 = `f(视频)`」同性质：**不是作者内容，是可重算的派生数据**。
派生数据就该存本地、可丢弃、可重算，而不是当成不可变事实写进 E2EE 密文。由此带来三个好处：

- **E2EE 承诺不动**（服务器看不见任何东西）；
- **模型升级可回填**：换更强的模型后对历史语音重转即可，无需任何同步；
- **换机也稳**：新设备从服务器拉回密文音频、解密后自己重算，不依赖旧设备。

## 3. 为什么不选其他方案

| 方案 | 否决理由 |
| ---- | -------- |
| 发送端转写、并入消息密文 | 把旧模型的错误结果**永久固化**在服务端密文里，模型升级无法改进 |
| 云端 ASR（讯飞/阿里/OpenAI） | 要上传**明文音频**，直接违背 E2EE |
| 系统原生 API（`SFSpeechRecognizer` / Android `SpeechRecognizer`） | iOS 中文离线模型要联网下载；Android 依赖 Google 服务，国产机基本不可用；Flutter 插件多为**麦克风流式**设计，不适配「转写已有音频文件」 |
| 真·消息编辑（更新已有 messageId） | 现有消息**不可变**（`LocalMessages` 以 `messageId` 为主键、无编辑字段；协议无编辑帧），要动 wire + 服务端 + 回执/焚毁/序列对齐，代价过大 |
| 「先发音频、后台转写、再补文字合并」 | 系统不会自动合并两条消息；构造合并机制复杂，且同样会固化旧结果 |

## 4. 技术选型

- **引擎**：`sherpa-onnx`（k2-fsa，Apache-2.0）。官方 Flutter 包 `sherpa_onnx`（FFI），
  同时覆盖 iOS / Android；非流式离线识别。
- **前端处理**：可选 Silero VAD 切掉录音两端的静音，提升准确率、缩短耗时。
- **音频格式**：ASR 需要 **16 kHz 单声道 PCM**。语音消息时长上限 **60s**（`chat_page.dart`）。
  2026-10-10 起录音改存 **16 kHz 单声道 WAV**（见 §8，老板拍板）——`record` 直接出 wav、零转换；
  旧消息维持 m4a（播放不受影响，转写入口提示"旧格式不支持转写"）。

## 5. 模型选型（SenseVoice vs Paraformer）

| 维度 | SenseVoice-Small | Paraformer-zh-small |
| ---- | ---------------- | ------------------- |
| int8 体积 | **≈ 230 MB** | **79 MB** |
| 语言 | zh / 粤 / en / ja / ko | 中 + 英（含河南/天津/四川口音） |
| 口语 / 方言 | **更稳**（训练数据多样、含口语与多方言） | 标准普通话强，非正式场景下降 |
| 中英混说 | **支持好** | 一般（超出中英即掉） |
| 标点 | **自带标点 + ITN**（数字规整） | 待核实：sherpa-onnx 版常需**另配标点模型**（CT-Transformer，约几十 MB） |
| 速度 | 快 | **更快** |
| 额外输出 | 带情感/事件标签，需**剥离**后展示 | 纯净文本 |
| 许可 | Apache-2.0（**模型许可需再核**） | Apache-2.0 |

**结论：默认选 SenseVoice-Small**（老板 2026-10-09 定）——**先按它落地**，Phase 0 用真实语音 A/B 后最终确认。
理由（按重要性）：

1. **标点基本是决定性的**：气泡下挂一行转写文字，有无标点直接决定可读性。SenseVoice 一个自包含模型
   直接出带标点的句子；Paraformer 在 sherpa-onnx 里通常要再配一个标点模型（CT-Transformer），
   省下的体积与复杂度又被吃回去（此点标"待核实"，Phase 0 确认 Paraformer 原生输出是否带标点）。
2. 本产品内容是**情侣/熟人日常口语**，SenseVoice 训练数据更偏口语/多方言，更贴场景；
   Paraformer 在正式标准普通话上更准，但本产品用不到那个优势。
3. **中英混说**在日常聊天里很常见，SenseVoice 明显更稳。
4. 体积不是主要顾虑：只有两台自用设备、又是侧载，230 MB 打包进产物可接受（不进 git，build 时脚本拉取）。
   且 §2.1 的「可换模型 + 可重算」意味着**这不是锁定**——真机效果不满意，换 Paraformer 重转即可，零迁移成本。

**降级条件**：若 Phase 0 真机实测「Paraformer-zh-small 的口语识别 + 标点」在实际语音上够用，
则改用 `Paraformer-zh-small`（79 MB、更快）作为移动端更省的方案。

> Phase 0 复核：用**老板的真实语音**对两模型各跑一遍，比较「口语短句 / 中英混说 / 标点」三项，据此最终定。

## 6. 架构与数据流

```text
发送端：点输入盒内合并图标进提示态 → 长按录音条录音 ─► 本地明文音频文件 ─►（加密上传，流程不变）
                                      └─► 后台 isolate: ASR ─► 本地转写表 ─► 气泡下方显示文字

（录音入口交互 2026-10-25 调整：麦克风/键盘两个入口合并为输入盒内左侧一枚自制
图标（麦克风+文档，Vocie transcription 同款），点击=文字态↔语音态互换；四态
（文字/提示/录音中/预览）与「长按录音条开录、松手停」手势保留不变。录音中或预览态
点图标切回键盘会**保留**已录内容，再点可直接回预览态用；X 删除后回提示态。
详见 aimemo/worklog/20261025T*.json 与 chat_page.dart `_onVoiceEntryTap`。）

接收端：收到消息 ─► 下载密文附件 ─► 解密为本地明文 ─► 后台 isolate: ASR ─► 本地转写表 ─► 显示
```

- 两端**各自独立**转写，互不通信；转写文本**不产生任何网络流量**。
- 转写在**后台 isolate** 串行执行，避免抢 UI 线程、避免并发抢 CPU。

## 7. 数据模型

新增 drift 表 `LocalVoiceTranscripts`（**升一版 schema**）：

| 列 | 说明 |
| -- | ---- |
| `messageId` | 主键，外键 → `LocalMessages(messageId)`，**级联删除** |
| `text` | 转写结果 |
| `modelId` | 模型标识（如 `sense-voice-small`） |
| `modelVersion` | 模型版本/文件哈希——**判断是否需要重转的开关** |
| `audioSha256` | 音频密文 sha256——音频若变化则转写失效 |
| `language` | 识别到的语言（SenseVoice 会返回） |
| `status` | `pending` / `done` / `failed` / `stale` / `unavailable` |
| `updatedAt` | 时间戳 |

**关键约束**：

- 该表**纯本地**，不进 E2EE 密文、不参与同步、**服务端不可见**。
- **随消息级联删除**：音频被阅后即焚或删除时，转写必须同时消失。
- **备份按"可丢弃缓存"处理**：能从密文音频重算，不写进备份快照（避免把可能不准的文字带进备份）。
- `modelVersion` 或 `audioSha256` 变化 → 标记 `stale`，可重转。

**schema 版本号教训（2026-10-22）**：新表起初挂在 `from < 10` 迁移块里，但 v10（墓碑来路列）已随 main 发布——已升到 v10 的存量库（生产/dev 都是）再打开时 `from==10`，整段迁移不跑，**新表根本不存在**，转写行的 drift watch 流直接报 `no such table`。新增表**必须占独立版本号**（本例 v11 + `from < 11` 块），与"已发布的最高版本"错开。回归用例：`local_database_migration_test` 的「v10 存量库打开 → 补建表并升 v11」。

## 8. 音频格式问题（必须解决）

ASR 输入需 16 kHz 单声道 PCM，现有录音是 m4a/AAC。三条路：

1. **【推荐】语音消息改存 16kHz 单声道 WAV**（`record` 可直接出 wav）：ASR 零转换、无额外依赖；
   代价是体积约 8×（60s ≈ 1.9 MB，个人自用可接受）。旧消息维持原样、不强制转写。
2. 保留 m4a，转写前**解码为 PCM**：需引入解码能力（`ffmpeg` 类库体积大且在维护上有风险，
   或走平台原生 `MediaCodec` / `AVAudioConverter` 平台通道，工作量大）。
3. 录音同时**旁路录一份 wav** 仅用于 ASR：改动录音链路，双写文件。

**已拍板（老板 2026-10-10）：采用方案 1**——录音改 `AudioEncoder.wav` + 16kHz 单声道（`record` 直接支持）。

> **⚠️ macOS 容器的坑（2026-10-23 实测修复）**：`record` 插件在 macOS 走
> AVCaptureAudioFileOutput，录音产出形态不稳定，实测踩到两个坑：
> ① **WAVE_FORMAT_EXTENSIBLE 容器**（tag=0xFFFE，JUNK + 40 字节 fmt + FLLR + data）：
> 数据是标准 16bit 交错 PCM，但 sherpa-onnx 的 wave-reader 明确不支持该容器
> （"We don't support WAVE_FORMAT_EXTENSIBLE files."），服务端当时也只认 tag=1；
> ② **44.1kHz/32bit IEEE float 的 extensible**（GUID=3）：录音器没拿到 16kHz 时
> 回落写设备原生格式——采样率/位深都不对，且实测真实录音里还混有 NaN/Inf 故障帧
> （float 采集毛刺，直接让量化抛 "Infinity or NaN toInt"）。
> 修法：`VoiceTranscriptService.normalizeWavBytes` 全形态归一——16k PCM 只换 44 字节
> 标准头（数据一个采样点不动）；float/非 16k 线性重采样到 16kHz + 转 int16，
> NaN/Inf 按静音处理。三个调用点：**录音落库前**（`_stopVoice`）、**本地转写喂
> isolate 前**（`_processOne`，覆盖存量）、**服务端上送前**（`_serverVoiceTranscribe`）。
> 服务端 `wavDurationMs` 同时改成接受 extensible（子格式 GUID 为 PCM 时），双保险。

> **⚠️ macOS 设备格式的坑（2026-10-25 老板 iMac 实测修复）**：iMac（iMac19,1）**重启后**
> 内置麦克风 HAL 默认 Float32（`AVCaptureDevice.formats` 只列 Int16/Int24，当前格式是列表外
> 的 Float32），此时 AVCaptureAudioFileOutput 写 WAV 的文件链断——沙盒内
> `AudioFileCreateWithURL failed (fmt?)`（kAudioFileUnsupportedDataFormatError），非沙盒
> 直接 -11805 "The combination of audio file type and audio format in audioSettings is not
> supported"→ **0 字节文件、振幅流全静音**（UI：无波形 + 松手弹「录音内容为空」）。
> MacBook Air 麦克风默认即整数 PCM、9-24 正式版走 m4a/AAC，故两处都不坏（老板两机对照）。
> 修法：录音前（`_startVoice` 里 hasPermission 后、`recorder.start` 前）经 `einz.audio.input`
> 频道调 `lockInputDeviceToIntegerPcm`（MainFlutterWindow.swift）把默认输入设备锁到整数
> PCM（优先 16-bit、采样率最接近请求值）；已是整数则不动，失败静默不阻塞。锁一次持久到
> 下次重启。WAV + 纯虚拟设备（Teams 环回）不受此坑影响。

> **💡 路线复盘（2026-10-25）**：上面「设备格式的坑」与当初方案 2/3 的关系——坑的边界不是
> wav 容器，而是 **AVCaptureAudioFileOutput 的 WAV 写入链 × Float32 设备**这个组合：
> - **方案 3 用文件 API 旁路**（同会话加第二个 file output / 第二个 recorder——插件唯一的
>   文件写入就是它）→ 照撞此坑，连 10-23 的 EXTENSIBLE 坑一起中；且症状更隐蔽：m4a 主文件
>   正常发出、wav 旁路静默为空 → 转写永远失败，UI 不弹「录音内容为空」。
> - **方案 3 走流式旁路**（`startStream` = AVAudioEngine `installTap` + 插件自带
>   AVAudioConverter 转换拼 PCM，源码 RecorderStreamDelegate.swift 已核实）→ 免疫，
>   不经 AVCaptureAudioFileOutput。
> - **方案 2**（m4a + 转写时解码成 PCM）→ 完全绕开：wav 由解码器产出，与采集链无关
>   （代价是 ffmpeg 依赖或平台通道工作量，即当年否掉它的原因）。
> 教训：只要「从采集端直接产出 wav」，设备格式问题就绕不开，与选哪条路线无关；今天的
> 预锁修复是让采集端直出 wav 在 iMac 上可靠的前提。
协议层加 `meta.voiceContainerWav=true` 标识新消息（旧消息无此键 = m4a；`docs/PROTOCOL.md` §5.1 已登记），
`_voiceExtOf` 在播放/转写/留存目录/手动入口四处统一扩展名口径；旧 m4a 消息播放照常（系统 AAC 解码），
手动转写入口点按提示"旧格式不支持转写"，不打哑炮。体积代价 60s≈1.9MB 可接受；wav 音质
未真机 A/B（若出问题可回退方案 2 解码，存量数据不受影响）。

## 9. 触发与调度

- 收到消息且**音频已解密**（附件 `status=downloaded` 或本机即发送端）→ 入本地转写队列。
- 队列在**后台 isolate 串行消费**；失败重试上限（建议 2 次）后置 `failed`。
- 模型未就绪（未打包/未下载）→ 置 `unavailable`，UI 不露破绽（见 §10），提供手动入口。
- **不做**"升级后全量批量重转"：CPU 密集。倾向**惰性重转**（进入会话/展开该条时才重算）或显式按钮。

## 10. UI

- 气泡：现有**波形 + 秒数**保留，**下方加一行转写文字**。
- 转写中：占位（骨架/「转写中…」）。
- 失败 / 未就绪：显示可点的**手动转写**入口，不显示错误堆栈。
- `stale`：显示「可重新转写」入口。
- 来源图标（老板 2026-10-23）：所有状态（done/pending/failed/stale/unavailable）行首
  都带来源图标——云=服务端 whisper（modelId `whisper-server`，明文音频出过本机），
  芯片=本地 sense-voice。失败/未就绪行同样带（modelId 在失败写入时就已落定：
  本地失败=`sense-voice-small`，服务端失败=`whisper-server`），点按重试不改变来源判断。
- 注：转写可能不准，**不提供编辑**（本期）；如未来要允许用户改文字，则性质从"缓存"变为
  "用户内容"，需重新讨论存储与备份策略。

## 11. 模型分发（2026-10-12 改回：打包进产物，首次转写就地解包）

| 方式 | 优点 | 代价 |
| ---- | ---- | ---- |
| **打包进产物**（build 时脚本拉取，**不进 git**） | 装好即离线可用、无下载逻辑 | 产物 +239 MB |
| **首次使用时下载** | 产物小 | 需处理下载/进度/失败/存储 |

**结论（2026-10-12 老板拍板，改回打包；2026-10-25 再改为开关可选）**：模型
二进制**不进 git**，由 `scripts/fetchVoiceModel.sh` 拉取到
`app/assets/voice_model/`（幂等：已就绪秒过；双源 + 3 轮重试；sha256 校验）。
**2026-10-25 起 pubspec 基线不再声明 `assets/voice_model/`**——只有
`VOICE_MODEL=true` 时由 `scripts/insertVoiceModel.sh` 拉取模型、临时注入
声明并执行 flutter 命令，结束（含失败）trap 还原。运行时**首次转写前**由
`VoiceTranscriptModel.ensureInstalled` 装到
`<ApplicationSupport>/voice_transcript/<kModelVersion>/`——已装过（含 10-10
~10-12 期间下载过模型的设备）直接复用，**零迁移**。

分发链路（`app/lib/data/voice_transcript_model.dart`）：

- **三级解析** `ensureInstalled`：① `installedDir` 命中 → 直接用；
  ② 包内有资产（`rootBundle.load('assets/voice_model/…')`，缺失时 manifest
  快速失败不会真读 239MB）→ 拷进应用目录（model.onnx 分 1MB 块写：平滑
  进度 + 可取消 + 取消清残file；只校验大小——资产由 App 签名保护完整性）；
  ③ 包里没有（dev 构建没跑 fetch 脚本）→ **回落 `ensureDownloaded` 下载兜底**，
  dev 机不断网也能自愈。
- 下载兜底双源：hf-mirror.com 优先（大陆可达），失败回落 huggingface.co；
- 下载断点续传：`.part` 临时文件按已收字节 Range 续传（仅对**同一主机**有效——换源前清 `.part` 重下）；
- 下载完整性：大小 + sha256 边下边算（不把 239MB 读进内存），基线见 `_files`
  （model.int8.onnx 239233841B / tokens.txt 315894B，sha256 为 2026-10-10 基线；
  **与 fetchVoiceModel.sh 基线同一份，改模型两处一起改**）；
- 原子性：全部文件就绪后才写 `.ok` 标记，不完整目录视为未安装；

## 15. 方案 D'：服务端自建 Whisper 转写 [待评审]（2026-10-18 老板提出）

### 15.1 背景

打包 239MB 模型进产物（或让用户首次下载）成本都过高，老板提出换思路：
**录音明文发给后台，由服务端自建 Whisper（faster-whisper/whisper.cpp，CPU 推理）转写**，返回文本。
2026-10-18 老板初步拍板：① 服务端**自建**（不走 OpenAI 等第三方 API）；
② 本地模型链路（§11）**暂时保留**，等想清楚再删；
③ 授权粒度在菜单里设选项——用户可选「全部语音自动转写」或「单条显性授权」，
甚至可选「下载模型本地转写」还是「后台转写」。
（**2026-10-23 重构落地**：拆成两组——「转写方式」本机/服务端二选一 + 「自动
转写」开关；「每条询问」不再是并列选项，而是自动关闭时（默认）的行为。见 §15.4。）

### 15.2 关键设计问题：明文怎么到服务端（2026-10-18 讨论结论）

**老板的设想**：服务器存的仍是密文；收件人（或发送端）在本地解密音频后，
把**解密后的明文**再发给后台的转写接口。

**评估：可行，且是几个候选里最合理的**。候选方案对比：

| 方案 | 做法 | 评价 |
| ---- | ---- | ---- |
| **A. 客户端解密后上送明文**（老板设想） | 收/发端已有明文 wav，直接 `POST /transcriptions` 上传音频，服务端转写后返回文本、**即转即删** | ✅ **推荐**。零协议改动（服务端本来就有 attachment 接口，新增一个 multipart 端点即可）；明文暴露范围 = 运营者自己，与现状「服务端可见元数据」同级；实现最简单 |
| B. 服务器自己解密（托管 space_key） | 需要密钥上服务器，E2EE 完全破功 | ❌ 否决——比 A 暴露面大得多，且破坏「服务端永不持有密钥」不变量 |
| C. 两方计算 / MPC 保密转写 | 密码学手段让服务端转写但不「看见」音频 | ❌ 研究级复杂度，CPU 开销巨大，whisper 场景无成熟方案 |
| D. TEE（SGX/SEV 跑 whisper） | 硬件可信执行环境 | ❌ VPS 不一定支持，运维复杂度不成比例 |

**A 方案要点**：
- 暴露的只是「用户主动要求转写的那条录音」，且**即转即删**——服务端不落盘明文音频
  （内存里过一遍 whisper 就丢），审计日志只记事件不记内容；
- 与现状对比没有引入**新的第三方**：服务器运营者（老板本人）本来就能看到元数据、
  能推消息，现在多了「在用户授权时听到一段几秒即删的录音」；
- 本地转写表 `LocalVoiceTranscripts` 结构完全复用（`modelId` 记 `whisper-…`），
  stale/重算/级联删除语义不变；
- UI 授权选项（§15.1 ③）落点：设置页三选一——「本地转写（需下载模型）」/
  「服务端转写（录音将发送到服务器，转写后立即删除）」/「每条询问」；
  全部语音自动转写仅在用户显式选择后生效。
- 已知权衡：E2EE 产品叙事从「服务器看不见任何附件内容」收窄为
  「服务器看不见附件内容，除非你使用服务端转写功能」——文案必须明示。

### 15.3 优化：发送时双传（密文 + 明文）[待评审]（2026-10-18 老板提出）

**老板设想**：用户发送语音时，**同时上送密文和明文**——密文照旧落盘保存（E2EE 不变），
明文仅供服务端转写后即转即删。这样转写在发送时就已完成，任何客户端要转写结果
时**不再需要单独上传明文的那次往返**。

**评估：方向正确，且收益比「省一次往返」更大**。真正的本质是——

> 把转写从「各端本地各算一遍（D 方案）」变成「**服务端算一次、全体共享**」。

这才是省钱的来源：不是省一次上传 RTT，而是省了 **N 台设备的本地 ASR 计算**
（CPU/电量）+ **N 份 239MB 模型的下载/打包**。服务端 CPU 上跑一次 whisper，
比每台手机各跑一次本地 ASR 划算得多，而且所有端看到的转写结果**一致**。

**但有一个必须钉死的点——发送时带明文必须是「条件行为」**：

| 用户设置 | 发送时是否带明文 | 转写何时算 |
| ---- | ---- | ---- |
| **全部语音自动转写** | ✅ 带（密文 + 明文一次传） | 服务端发送时即算，结果存服务端共享 |
| **单条显性授权** | ❌ 不带（只传密文） | 用户在某端点「转写」时，走 §15.2 的 D' 按需流程（该端上送自己解密的明文） |

**不能无条件带明文**：否则等于**所有**语音消息的明文都自动上服务器了，
直接和菜单里「单条显性授权」选项自相矛盾，也把 E2EE 破口从「按需」放大到「全量」。
条件化后，隐私暴露粒度才和用户的选择对齐。

**随之而来的架构变化（需老板知情并主动认领）**：

1. **转写结果的归属变了**：从「各端本地派生数据（§2.1 哲学：本地、可重算、不进密文、不同步）」
   变成「**服务端算好、存服务端、分发给各端**的共享产物」。这打破了 §2.1 的初衷，
   是 D' 方案的必然延伸，不是免费的——老板应明确接受这一点。
2. **转写结果在服务端怎么存**：明文音频已即转即删，但**转写文本**若要在各端共享，
   必须留在服务端一段时间（直到各端取走）。它应当**用 space_key 加密后落盘**
   （服务端不解析内容），与附件密文同等保护，避免「运营者磁盘上躺着明文文字」。
3. **焚毁联动**：阅后即焚触发时，密文、（残留的）明文、**转写文本**三者必须一起删。
4. **发送端自身**：录音者本机本来就有明文，发送端可选「用本地转写」或「等服务端结果」，
   不必强制走服务端——保留 §15.1 ③ 里「本地 / 后台」的可切换性。

**与 §15.2 的关系**：§15.2 的「客户端解密后按需上送」（D'）仍然保留，作为
**单条显性授权**模式的路径；本节是**全部自动转写**模式的优化路径。两模式并存。
