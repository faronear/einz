# 术语：东西都叫什么（命名分层）

状态：**2026-09-22 定稿**（老板；同日晚做了 UI 用词修订；**2026-09-23**：界面用词「入口」→「通道」（英文仍 `entrance`），见「命名约定」第 1 条；**同日代码/wire/DB 全量改名落地**，见「wire 字段改名」一节）。本文是**唯一**的分层定义，`docs/DATABASE.md`、
`docs/PROTOCOL.md`、`aimemo/` 下的设计与产品文档都以此为准。

## 为什么需要这份东西

多空间把原来含糊的"设备"劈成了三层：一台**物理机器**上可以装一份 App/TUI（**安装**），
一份安装可以进多个**秘境**，每进一个秘境就是一次**登记**（一套密钥 + 一个身份）。
这三层在代码里都叫过 "device"，于是同一句话经常指三件事。约定如下。

## 分层定义

| 层 | 定义 | 代码 / 字段 | 界面用词 |
| --- | --- | --- | --- |
| **物理设备** | 一台真实的机器（iPhone、MacBook…） | 无字段。只能靠旁证推断（IP、时间、push token、同型号同名，见下） | 不提（用户自己会说"我的手机"） |
| **安装** | 一台机器上的一份 App / TUI 部署（一份本地数据） | `install_uid`（客户端生成，**安装级**，卸载重装 / 整机清空即轮换；按通道的重置不动它） | 「本机」 |
| **登记项（通道）** | 某安装在某秘境里的一次登记：**本机 ⇄ 秘境的一条加密链路**（一套密钥对 + 一个身份 + 一个会话锚点） | `entrances` 表的**一行**；`entrance_id` | **「通道」**（英文 **entrance**，中英不同名，见命名约定 1） |
| **开通码** | 一次性进入授权：凭它可在某秘境里**开通一条新通道**。接收方中立——可给伴侣，也可给自己的另一条通道 | `join_tokens` 表、`POST /spaces/{id}/join-tokens` | **「开通码」**（英文仍 **token**，中英不同名） |
| **共享口令** | **两人共同持有**的口令，用于把 Space Key 封进服务器上的密保箱（key escrow）：新通道凭它取回密钥；任一方也能用它做撤销通道的二次校验 | `key_escrow` 表（argon2id 哈希）；**客户端不落盘** | **「共享口令」**（英文 **shared passphrase**；短引用可用「口令」） |
| **伴侣 / 成员** | 秘境里的两个身份（slot 0 = 创建者，1 = 第二人） | `space_members.partner_id`、`space_members.slot`（同一身份可多条通道共享） | 「我的身份 / 对方」 |
| **秘境（空间）** | 两位伴侣的私密世界 | `spaces.space_id` | 「秘境」（空间列表页叫「我的空间」） |

一句话记忆：**一台机器 = 一个安装；一个安装 × 一个秘境 = 一个登记项 = 一条通道。**

### 这不是一条链，是一张网（通道有两个父层）

通道是「**安装 × 秘境**」的**交点**，不是"秘境 → 通道 → 安装"的中间层：

```text
物理设备（无字段，只能靠旁证推断：IP / 时间 / push token / 同型号同名）
└── 安装  install_uid = A…            ← 一份 App/TUI 的可运行拷贝（一份本地数据）
    ├── 通道 e1 ── 秘境「家」          ← 交点：A… × 家
    ├── 通道 e2 ── 秘境「旅行」
    └── 通道 e3 ── 秘境「测试」
```

服务端凭 `e1/e2/e3` 的 `install_uid` 相同 → 知道"这几行是同一台机器"（仅内部认知，
**绝不进任何响应体**）。

### 各层各有哪些数据（**别把秘境级的说成通道级**）

| 层 | 它那一半是什么 |
| --- | --- |
| **通道级** | entrance 自己的 X25519 **身份密钥对**（challenge-response 认证用）、`entrance_id`、`partner_id`、session token、`entrance_name`、指向安装的 `install_uid`、`status` |
| **秘境级** | **Space Key**（内容密钥，两位 partner 共享，走密保箱分发）、消息、附件、读水位（`receipts`） |

客户端里"本安装 ↔ 本秘境"是**一一对应**，所以本地数据一律按 `spaceId` 分命名空间
（`space.<spaceId>.*`、`local_messages.space_id`）——"这条通道"与"这个秘境"的本地足迹
重合，但**语义不同**：撤销一条通道不动秘境的内容密钥，也不动对方那条通道。

### 客户端粒度不对称（容易踩）

| 客户端 | "一个安装" = | 一个安装能挂几个秘境 | `install_uid` 的粒度 |
| --- | --- | --- | --- |
| **App** | 一份 App 安装 | **多个**（Vault 里装 N 份凭证） | 安装级——N 条通道共用同一份 |
| **TUI** | 一个 store 文件 | **恰好一个** | store 级——同机多 store 是刻意的"多安装"模拟 |

所以"`install_uid` 代表物理设备"这句话**只对 App 成立**；TUI 里它是 store 级。

## 命名约定

1. **界面用词（2026-09-22 晚定，2026-09-23：「入口」→「通道」）。** 三个词各管一段，**不再靠加限定词消歧**：
   - **「通道」= 本机 ⇄ 这个秘境的那条链路**（英文 `entrance`）：菜单项「通道名称」、
     弹窗「通道信息（本秘境）」；「邀请新设备」这类说法换成「开通一条新通道」。
     中英**不同名**（2026-09-23 定）：zh=「通道」、en=`entrance`——英文不用 `channel`（会被读成 Slack/WebSocket/Go channel）、也不用 `passage`（与同屏的 `passphrase`「共享口令」同根相近）；中文取「通道」是因为它锚住两端、动宾搭配更顺。两端各自取最优，不追求逐字对应。
   - **「本机」= 这台物理机器**（英文 device）：「仅本机生效」「本机锁屏码」
     「两台设备需要连同一台服务器」。
   - **「开通码」= 一次性进入授权**（英文仍 `token`，2026-09-23 起；取代「令牌」，更早是「邀请码」）。
     **为什么从「邀请」改**：原词「邀请」预设接收方是**别人**，而开通码**也可以用在
     自己另一台设备上**（join 流程里那步「选择我的身份」正是因为这个二义性才存在）；
     它对接收方中立，且与代码 `join_tokens`、协议文档里的 "join token" 对应。
     **为什么再从「令牌」改「开通码」（2026-09-23）**：①「令牌」偏技术黑话，
     「开通码」直述用途——凭它**开通**一条新通道，与通道术语的动词（开通/销毁一条通道）
     连成一条语义线；②中英**不同名**（zh=「开通码」、en=`token`），同「通道/entrance」
     先例：两端各取最优，不追求逐字对应。代码 `join_tokens` / wire 字段按第 2、3 条约定不改。
   - **「共享口令」**（英文 `shared passphrase`，2026-09-22 晚定）：取代原「密保口令」。
     为什么改：它是**两人共同持有**的凭证（创建者设定后告知对方；任一方都能重设，
     重设后另一方必须被通知）——原词"密保"是**机制词**（密保箱 / key escrow），
     描述的是"存放在哪"而不是"这是什么"。改名后把所有权写进名字里，
     原先要靠一整句 hint 教学的那件事（"口令是与伴侣共享的…"）就自明了。
     短引用可省成「口令」（如「旧口令 / 新口令 / 口令错误」），**密保箱**作为机制词保留。
   - **「邀请链接」保留**（英文 `invite link`）：指向 `/join/<token>` 的那个链接。
     它**承载**开通码，而且那个地址打开就是一个**带欢迎辞与简介的落地页**（`PROTOCOL.md`
     里叫「邀请落地页」）——"邀请"正是它的含义，所以"复制邀请链接""把邀请链接发给我"
     都自然，不必改叫"开通码链接"。**开通码**指那条一次性授权本身（"填写开通码""开通码无效"）。
   - **为什么从「入口」改成「通道」（2026-09-23）**：①「入口」在中文代码里早已是"入口点"
     的通用词（语音入口、拍照入口、服务器入口、接入口令…），一词两义；「通道」作通用词
     用得少，专名性更强。②「入口」只锚住秘境那一端，而登记项的本质是**"安装 × 秘境"这个
     二元组**——「一条通道」天然自带两端（本机端的密钥与会话、秘境端的身份）。③现有文案的
     动词本来就是给「通道」配的：开通 / 销毁 / 撤销**一条**通道，比"开通一个入口"顺。
     **代价**：「通道」偏"连接"的画面，弱化了"身处秘境之中"的体验隐喻（「入口」更贴
     "走进去"）——取舍上取"更贴当前阶段要管理的对象"。
   - **「通道」的消歧**：本文的「通道」**专指登记项**。密钥 / 撤销语境里原用的「密文通道」
     「公钥通道」已改称**「链路」**（`SECURITY.md` / `E2EE.md` / `KEY_ESCROW.md`）；
     「平台通道」（Flutter MethodChannel）、「实时通道」「厂商通道（推送）」属平台实现语境，
     与界面术语不同层，维持原样。
2. **代码与文档用层名。** 代码/注释/日志一律用 `install` / `entrance` / `partner`
   语义命名，不要再造新的 "device" 概念（UI 层「本机 / device」除外）。
   **存量命名已于 2026-09-23 全量迁移**（见下节）。
3. **wire 字段名与界面用词同名分层。** `device_id` → `entrance_id`、`person_id` →
   `partner_id` 已落地（2026-09-23）：登记项一律叫 `entrance`，秘境内的身份一律叫
   `partner`，安装一律叫 `install`。

### 字段对照速查

| 看到 | 实际是 |
| --- | --- |
| `entrance_id`（表列 / JSON 键 / 路径参数） | 一个**登记项（通道）**的 id（安装 × 秘境），服务端 `randomUUID()` 生成 |
| `install_uid` | 一个**安装**的 id，客户端生成、随 create/join 上报、可补登；**绝不进响应体** |
| `entrance_name` | 登记项的显示名（老板 2026-09-22：**它本质是"通道名"**）。默认取设备型号——这是"一设备一通道一秘境"时代的历史遗留，用户可以改 |
| `partner_id` | 秘境内的**身份** id（两位伴侣各一），同身份多通道共享 |
| `slot` | 身份在秘境里的槽位（0=创建者，1=第二人）；旧名 `partner_slot` 已废弃 |
| `entrance_partner_map` | 本机维护的「通道 → 身份」映射（归属判定用） |
| `push_tokens.entrance_id` | 登记项 id（一个安装在每个秘境的通道各有一行） |

## wire 字段改名（**2026-09-23 已完成**）

改名计划与完整映射表见 **`aimemo/renamePlan.zhcn.md`**。要点：

- `device_id` / `device_name` → **`entrance_id` / `entrance_name`**（登记项）；
- `device_uid` → **`install_uid`**（安装）；
- `person_id` / `person_name` → **`partner_id` / `partner_name`**（秘境内的身份）；
- `partner_slot` → **`slot`**；旧 `partner_name`（第二人）→ **`peer_name`**，
  创建者一侧用 **`creator_name`**；
- 表 `devices` → `entrances`、`device_activity` → `entrance_activity`；
  路由 `/devices/*` → `/entrances/*`，成员改名 → `POST /partners/name`。

**为什么这次能一次做完**：全新上线、无老客户端、无历史数据 → 不需要双名窗口 /
协议版本双接受 / 读旧回退；**一次机械替换 + 一次提交**即可，故不做三期 alias。

**HTTP 路径**：`POST /auth/challenge` 的请求体字段已随改名变成 `{entrance_id, space_id}`；
撤销走 `POST /entrances/:id/revoke`。

## 物理设备的旁证（为什么真有需要时也能认出来）

服务端本来就能概率性地把同一台机器的多个登记项关联起来：审计表里的 `ip`
（`connection_events` / `entrance_activity`）、在线时间互斥的切换模式、push token
（同一安装注册的是同一个 APNs token）、以及默认取型号的 `entrance_name`。
`install_uid` 的作用是把这件事从"概率推断"变成"确定性事实"——它只做**服务端内部认知**，
不参与授权，也不进任何响应体（见 `aimemo/multiSpaceDesign.zhcn.md` §3.7）。
