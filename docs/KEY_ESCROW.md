# 口令托管密钥（Passphrase-Protected Key Escrow）方案

> **状态：`[已实现]`**（2026-08-29 落地：Server 三端点 + shared KeyEscrowService + CLI escrow 命令 + App 接入口令/凭口令接入/rotate 自动重传；Server 冒烟、shared 16 项、App 18 项、CLI 全链路与双端 e2e 全过）。
> **版本适用：** 本文主体描述 **v1 单空间（`v1-single-space`）** 的托管与"白名单"语境；
> Multiverse（`v2-multiverse`）下空间与成员改由 `POST /spaces` / `join` 建立、按
> `space_id` 隔离，托管包读写见 `PROTOCOL_MULTIVERSE.md` §4.2（2026-09-15 起上传分支需
> 该空间成员会话，口令取包分支仍免认证）。
> **定位：** 在**不推倒现有 E2EE**（Server 只见密文）的前提下，解决"换设备 / 朋友新接入门槛高"的痛点。
> **相关文档：** docs/E2EE.md（协议）、docs/DEPLOYMENT.md §2.2（当前 seal/import 分发）、docs/PROTOCOL.md §7.4（协议增补）

---

## 1. 背景与动机

### 现状（客户端持有 Space Key）

- Space Key 由设备 A 随机生成，用设备 B 的公钥密封（密保信封）后离线传递，B `import` 解出；
- 换手机/新设备 = 重新走一遍"生成密钥 → 公钥密封 → 传递 → 导入"流程（或依赖 12 词恢复码）；
- 朋友是非技术用户时，`import` 密保信封的操作门槛高。

### 痛点

| 场景       | 现状体验                                             |
| ---------- | ---------------------------------------------------- |
| 朋友换手机 | 需要老板重新 seal 一份 → 朋友再 import，步骤多、易错 |
| 老板换手机 | 同样要重走传递流程（App 侧目前是重贴密保信封）       |
| 设备丢失   | 靠恢复码兜底，恢复码本身也容易丢                     |

### 目标

1. 新设备/朋友接入**只凭一个口令**即可完成，无需 seal 传递；
2. **不改变"Server 只见密文"的承诺**——Server 存储的密钥包是密文，没有口令解不开；
3. 复用现有密码学基建（backup.dart 的口令派生 + AEAD），最小改动。

## 2. 方案概述

```
┌──────────┐  ① POST /key-escrow（上传密文包）   ┌──────────────┐
│  客户端   │ ─────────────────────────────────▶ │    Server    │
│（持口令） │                                     │（存密文包，   │
│          │ ◀───────────────────────────────── │  无口令不可解）│
└──────────┘  ② GET /key-escrow（拉取密文包）    └──────────────┘
```

- **Space Key 仍由客户端生成**（或首次设置时生成），从未以明文出过客户端；
- 客户端用**口令**（用户设定的接入口令）经 **Argon2id** 派生密钥，对 `{space_key, space_id, key_version}` 做 **XChaCha20-Poly1305** 加密，得到"密钥密文包"；
- 密文包**上传托管到 Server**（与消息无关，Server 只存不读）；
- 新设备接入：输入口令 → 从 Server 拉取密文包 → 本地解出 Space Key → 进入空间；
- Server 即使被攻破 / 备份泄露，拿到的只是密文包；没有口令（高熵慢哈希保护）解不开。

> 与业界对齐：Apple iCloud 高级数据保护、Signal PIN、WhatsApp 加密备份均为同一模式——**密钥加密后托管，口令只留在客户端/用户脑中**。

## 3. 密码学设计（全部复用现有实现）

| 组件       | 机制                                                                | 现有出处                                                |
| ---------- | ------------------------------------------------------------------- | ------------------------------------------------------- |
| 口令派生   | Argon2id（sodium_sumo pwhash，opsLimitModerate / memLimitModerate） | `shared/lib/src/crypto/backup.dart` `derivePassphraseKey()` |
| 加密       | XChaCha20-Poly1305（AEAD，随机 nonce）                              | 同上 `encryptWithPassphrase()`                                  |
| 密文包格式 | `{format, salt, nonce, ciphertext}`（base64）                       | 同上 `PassphraseEnvelope`                                       |
| 盐         | 每次托管随机生成（16B，`crypto_pwhash_SALTBYTES`），防彩虹表       | 同上 `generatePassphraseSalt()`                             |

**口令要求（2026-09-15 起）：** ≥ **8 位**（**只卡长度，不卡字符种类**）——规则唯一来源
`shared/lib/src/crypto/passphrase_policy.dart`，App（创建/改口令）、TUI（创建/`/passphrase`）、
CLI（`escrow upload`）在**设置/修改**时校验并提示；**输入既有口令不校验**（避免把已有短口令的
用户挡在门外）。更推荐"三个不相关的词 + 数字"这种词串（熵更高且好记）。

**防爆破（2026-09-14 订正）：** 原文写"口令验证发生在客户端，Server 不参与"——已过时。现在
**服务端参与验证**：`key_escrow.passphrase_hash` 存 argon2id 串，取包端点
`POST /spaces/{id}/key-escrow` 由服务端 `pwhashStrVerify` 校验（`server/src/escrow.ts`）。
因此防线是三层：

1. **口令强度**（上方策略）——这是主要防线：拿到 hash 后的**离线**爆破无法被限速，只能靠熵；
2. **服务端失败限速**——按 space 计失败次数，窗口内超限返回 429 `ESCROW_RATE_LIMITED`
   （默认 10 次 / 15 分钟，可用 `EINZ_ESCROW_RATE_MAX`、`EINZ_ESCROW_RATE_WINDOW_MS` 调参）；
3. **Argon2id 慢哈希**（moderate：256 MiB / 3 轮）——单次验证本身就贵。

> 限速是"防在线爆破"，**防不住**已获取 hash 的离线爆破；且按 space 限速意味着攻击者可
> 用失败尝试把合法取包暂时挡在窗口外（影响面：延迟接入，不丢数据）。

## 4. 协议设计（PROTOCOL.md 增量）

### 4.1 新端点

| 端点          | 方法   | 请求                                                | 响应                 | 说明                                      |
| ------------- | ------ | --------------------------------------------------- | -------------------- | ----------------------------------------- |
| `/key-escrow` | POST   | body: `{ package: {format,salt,nonce,ciphertext} }` | `{ok:true}`          | 上传/更新密文包（UPSERT，按 device 维度） |
| `/key-escrow` | GET    | —                                                   | `{ package: {...} }` | 拉取密文包                                |
| `/key-escrow` | DELETE | —                                                   | `{ok:true}`          | 清除（撤销/换绑时）                       |

- 认证：现有 Bearer session_token（challenge-response 后获得），与消息接口一致；
- 权限：**白名单内任一设备**可 GET（两人中任一人持口令即可帮对方接入）；POST/DELETE 仅限本人设备；
- Server 存储：复用现有 SQLite（新增 `key_escrow` 表：`device_id` 主键 + `package` + `updated_at`）；
- Server **永远不解析 package 内容**（存原样 JSON，校验仅限字段类型）。

### 4.2 幂等与冲突

- 同一 space 下任一方更新密文包，另一方拉取到的永远是最新一份（按 `updated_at` 最新者胜）；
- 简化约束：**密文包按 space 维度存一份**（而非按设备），`space_id` 主键——避免两份包不一致；任一方更新即覆盖，双方口令必须相同（或各自记住自己的口令，但包内容加密钥匙是同一口令派生）。

> **决策点（待审核）**：按 space 存一份（双方必须用同一口令）还是按设备存两份（各自口令）？推荐**按 space 一份**——语义简单，口令由老板告知朋友，天然一致。

### 4.3 与现有接口的关系

- 不修改任何消息/同步/附件接口；`seal`/`import` 流程**保留**作为无口令的离线兜底（不强制迁移）；
- `/key-escrow` 与现有备份/恢复（backup.dart）正交：备份是**文件级**全量，key-escrow 是**在线接入**辅助。

## 5. 新设备 / 朋友接入流程

```
朋友侧（新手机，仅需口令）：
① 设置页：服务器地址 + Space ID + 口令
② 客户端生成设备凭证（公钥/私钥）
③ 白名单登记：公钥发给老板 → 老板加入 config.json 重启（现有流程，不变）
④ 认证通过（challenge-response，现有流程）→ GET /key-escrow 拉密文包
⑤ 输入口令 → 本地 Argon2id 派生 → 解出 Space Key → 进入聊天页
⑥ （可选）App 设置启动锁 PIN（现有功能）

老板侧：
① 设置页输入口令 → POST /key-escrow 上传密文包（一次性）
② 之后朋友/新设备按上述流程凭口令接入
```

**相比现状**：朋友不需要拿密保信封文件、不需要理解"密封"概念——只需要知道一个口令。

## 6. 安全分析

### 威胁模型（目标：Server 与任何无口令者不可解密）

| 攻击场景                         | 结果                                                        |
| -------------------------------- | ----------------------------------------------------------- |
| Server 被入侵 / 数据库与备份泄露 | 仅得密文包；无口令解不开（Argon2id + XChaCha20）            |
| 运维人员读取数据库               | 同上                                                        |
| 口令泄露（老板告知场景）         | 知晓口令者可用任意设备接入——**口令即权限**，需谨慎保管      |
| 弱口令暴力破解                   | 被 Argon2id 慢哈希 + 熵要求抑制；客户端本地错误锁定（可选） |
| 密文包被篡改                     | AEAD tag 校验失败 → 解密报错，客户端提示重新拉取/重新上传   |
| 中间人（TLS 之外）               | 传输已走 HTTPS；密钥包本身密文，即使剥离 TLS 也无意义       |

### 与"取密文"的不对称（2026-09-14 补充）

取包**免设备认证**（口令即凭证）→ 知道口令就能拿到 Space Key；但**取密文**必须持白名单
设备 token（`/sync` 403）。所以"拿到密钥但没有密文 = 没用"——这也是撤销（掐密文通道）
优先级高于密钥轮换的原因，见 `SECURITY.md` §3.1。

### 剩余风险

1. **口令即权限**：知道口令 = 可解出 Space Key。私用场景（老板 ↔ 朋友）可接受，但口令应区别于 App 锁 PIN；
2. **Server 依然可见元数据**：消息时间线、双方在线状态等（现有设计，不在本方案范围内）；
3. **口令丢失**：与恢复码机制互补——口令丢了可用 12 词恢复码（离线）兜底；两者都丢则数据不可恢复（与 E2EE 一致）。

## 10. 验收标准（建议）

- [ ] 无口令时 Server 数据全为密文（抽查 DB 无法还原 Space Key）

- [ ] 既有功能回归：seal/import、收发消息、备份恢复全部不变

## 12. 口令更新与已认证设备（机制澄清与保留决策，2026-09-08）

**结论先行**：口令（escrow）更新后，已认证设备完全不受影响；"重新验证口令"的
被动更新机制（passphrase.rotated 广播 + 弹窗 + 离线补查）**保留**——它的价值
**不是为历史消息解密**，而是保持**本端口令缓存与服务器同步**。

### 12.1 为什么已认证设备不受口令更新影响

- Space Key 在接入（accessByEscrow）时用口令解密后**本地存放**；
- 历史消息/正常收发的加解密只用 Space Key，**不需要口令**；
- 因此口令更新后，已认证设备的正常使用、历史消息查看均无需新口令。

### 12.2 同步机制（按需检测 + 广播通知，2026-09-08 定案）

不弹窗打扰；分两通道：

1. **实时广播通知**：服务端广播 passphrase.rotated，客户端收到后**只发通知**
   （app SnackBar / TUI 系统消息插入消息流），不弹窗；
2. **上线补查通知**：App/TUI 上线/WS 重连时对比 getKeyEscrow 的 updated_at，
   服务端更新则发通知（不弹窗）——覆盖离线错过的广播。

> **2026-09-08 误报修复（rotated 显式标记）**："口令被重设"由**客户端显式声明**
> （POST /key-escrow 附 `rotated: true`，仅"修改口令"流程发送），服务端不比对
> passphrase_hash——argon2id 哈希自含随机盐（crypto_pwhash_str），同一口令每次
> 上传串都不同，比对必误判。
>
> **2026-09-14（客户端不再缓存口令）**：App 本地锁包/明文 payload 移除
> `escrowPassphrase` 字段，`lock_page._syncEscrow` 解锁自动重传整体移除——
> 服务器为唯一真相源，无本地口令缓存可"重传"，也无需普通重传去重。
>
> 密保箱重建（服务器数据丢失/被破坏）走"修改口令"流程（App 聊天页 ⋯ / TUI
> `/passphrase`）或 `cli escrow upload`。客户端按**服务器是否已有箱**分两种口径：
> ① 有箱 → 必须先用旧口令解开它（验证身份 + 防误覆盖）；② **无箱** → 旧口令
> 无从校验，跳过校验直接用新口令重建（设备已认证且持有 Space Key，不新增权限；
> 确认文案改为"重建"口径）。两种情形上传都带 `rotated: true`。

> **2026-09-08 降级 B（邀请码不再编入口令）**：此前邀请码二维码会打包
> spaceId+口令+邀请码（一键加入），生成时需"按需验证"口令避免编入旧口令。
> 因二维码含明文口令不安全，改为与 TUI 一致——邀请码分享只含邀请码，
> 口令由加入方另行输入（/space 或 App 口令步骤）；生成邀请码不再校验口令。

### 12.3 决策

**广播通知（app SnackBar / TUI 系统消息）+ 上线补查通知**（老板确认 2026-09-08）。
已认证设备正常使用/历史消息不受口令更新影响，故不强迫重输口令；只有修改口令
（/passphrase）时才要求输入旧口令验证。邀请码分享不携带口令（降级 B）。

## 13. 取消备份/恢复与全丢恢复（2026-09-08 / 2026-09-13 决策）

**核心结论：** 设备丢失 → 添加新设备即可；**双方设备全丢 = 双方放弃该空间**
（需要就重新建一个），因此不需要"恢复"。v1 时代之所以要有 `/recover`，是因为
v1 一台服务器只有一个空间、丢了就无法再建；Multiverse 下这个前提不存在。

**已移除（App，2026-09-08）：**
- 聊天页菜单「导出完整备份」（导出 EINZ-BACKUP 归档）；
- 设置页「全丢恢复」入口（⋯ 菜单）与「从完整备份恢复」折叠区（归档导入）；
- ChatPage.initialHistory 归档历史落库管线（死代码一并清理）。

**已移除（Server + TUI/CLI，2026-09-13）：**
- Server `POST /recover` 端点与 `recoverSpace()` 实现**整体删除**。三层原因：
  ① 它读的是 `key_escrow.space_id = ''` 那一行（v1 遗留），Multiverse 下密保箱存在
  `space_id = <真实 spaceId>`，所以**它本就永远读不到包**（线上只会 403）；
  ② 它的撤销逻辑是**全库范围**的——`UPDATE devices … WHERE status='active'`、
  `DELETE FROM sessions`、`DELETE FROM push_tokens`、`DELETE FROM invites` 都没有
  space 过滤，所以"把 ① 修好"反而会引爆成"撤销该服务器上**所有空间**的设备"；
  ③ "仅凭口令定位空间"根本做不到：服务端每个 space 只存一份 argon2id 哈希
  （自含随机盐），要凭口令反查只能遍历所有 space 逐个验哈希，而 Argon2id 故意很慢
  → 既是性能问题，又是免鉴权接口上的**放大攻击面**。
- TUI 引导里的"输入 r 全丢恢复"入口与 `_runRecoverAsCreator()` 一并删除；
  CLI/App 的 `recoverSpace()` 客户端方法、`Api.recover` 常量同步删除。
- `passphrase_hash` **保留**：它现在的用途是"加入方取口令密保箱时校验口令"。
