# 口令托管密钥（Passphrase-Protected Key Escrow）方案

> **状态：`[已实现]`**（2026-08-29 落地：Server 三端点 + shared KeyEscrowService + CLI escrow 命令 + App 接入口令/凭口令接入/rotate 自动重传；Server 冒烟、shared 16 项、App 18 项、CLI 全链路与双端 e2e 全过）。
> **定位：** 在**不推倒现有 E2EE**（Server 只见密文）的前提下，解决"换设备 / 朋友新接入门槛高"的痛点。
> **相关文档：** docs/E2EE.md（协议）、docs/DEPLOYMENT.md §2.2（当前 seal/import 分发）、docs/PROTOCOL.md §7.4（协议增补）

---

## 1. 背景与动机

### 现状（客户端持有 Space Key）

- Space Key 由设备 A 随机生成，用设备 B 的公钥密封（密钥信封）后离线传递，B `import` 解出；
- 换手机/新设备 = 重新走一遍"生成密钥 → 公钥密封 → 传递 → 导入"流程（或依赖 12 词恢复码）；
- 朋友是非技术用户时，`import` 密钥信封的操作门槛高。

### 痛点

| 场景 | 现状体验 |
| --- | --- |
| 朋友换手机 | 需要老板重新 seal 一份 → 朋友再 import，步骤多、易错 |
| 老板换手机 | 同样要重走传递流程（App 侧目前是重贴密钥信封） |
| 设备丢失 | 靠恢复码兜底，恢复码本身也容易丢 |

### 目标

1. 新设备/朋友接入**只凭一个口令**即可完成，无需 seal 传递；
2. **不改变"Server 只见密文"的承诺**——Server 存储的密钥包是密文，没有口令解不开；
3. 复用现有密码学基建（backup.dart 的口令派生 + AEAD），最小改动。

## 2. 方案概述

```
┌──────────┐  ① POST /key-escrow（上传密文包）   ┌──────────────┐
│  客户端   │ ─────────────────────────────────▶ │    Server    │
│（持口令） │                                     │（存密文包，   │
│          │ ◀───────────────────────────────── │  无口令不可解）│
└──────────┘  ② GET /key-escrow（拉取密文包）    └──────────────┘
```

- **Space Key 仍由客户端生成**（或首次设置时生成），从未以明文出过客户端；
- 客户端用**口令**（用户设定的接入口令）经 **Argon2id** 派生密钥，对 `{space_key, space_id, key_version}` 做 **XChaCha20-Poly1305** 加密，得到"密钥密文包"；
- 密文包**上传托管到 Server**（与消息无关，Server 只存不读）；
- 新设备接入：输入口令 → 从 Server 拉取密文包 → 本地解出 Space Key → 进入空间；
- Server 即使被攻破 / 备份泄露，拿到的只是密文包；没有口令（高熵慢哈希保护）解不开。

> 与业界对齐：Apple iCloud 高级数据保护、Signal PIN、WhatsApp 加密备份均为同一模式——**密钥加密后托管，口令只留在客户端/用户脑中**。

## 3. 密码学设计（全部复用现有实现）

| 组件 | 机制 | 现有出处 |
| --- | --- | --- |
| 口令派生 | Argon2id（sodium_sumo pwhash，opsLimitModerate / memLimitModerate） | `shared/lib/src/crypto/backup.dart` `deriveBackupKey()` |
| 加密 | XChaCha20-Poly1305（AEAD，随机 nonce） | 同上 `encryptBackup()` |
| 密文包格式 | `{format, salt, nonce, ciphertext}`（base64） | 同上 `BackupFile` |
| 盐 | 每次托管随机生成（32B），防彩虹表 | 同上 `generateBackupSalt()` |

**口令强度要求**：口令需满足最低熵（建议 ≥ 10 位混合字符，或 ≥ 5 个词）。口令不满足时客户端拒绝设置并提示。

**防爆破**：口令验证发生在客户端（解密失败 = 口令错），Server 不参与验证 → Server 侧无法限速；因此依赖：
1. Argon2id 慢哈希（单次尝试成本高）；
2. 口令高熵要求；
3. （可选增强）客户端侧错误尝试本地延迟锁定（对齐 App 锁的 5 次/30s 策略）。

## 4. 协议设计（PROTOCOL.md 增量）

### 4.1 新端点

| 端点 | 方法 | 请求 | 响应 | 说明 |
| --- | --- | --- | --- | --- |
| `/key-escrow` | POST | body: `{ package: {format,salt,nonce,ciphertext} }` | `{ok:true}` | 上传/更新密文包（UPSERT，按 device 维度） |
| `/key-escrow` | GET | — | `{ package: {...} }` | 拉取密文包 |
| `/key-escrow` | DELETE | — | `{ok:true}` | 清除（撤销/换绑时） |

- 认证：现有 Bearer session_token（challenge-response 后获得），与消息接口一致；
- 权限：**白名单内任一设备**可 GET（两人中任一人持口令即可帮对方接入）；POST/DELETE 仅限本人设备；
- Server 存储：复用现有 SQLite（新增 `key_escrow` 表：`device_id` 主键 + `package` + `updated_at`）；
- Server **永远不解析 package 内容**（存原样 JSON，校验仅限字段类型）。

### 4.2 幂等与冲突

- 同一 space 下任一方更新密文包，另一方拉取到的永远是最新一份（按 `updated_at` 最新者胜）；
- 简化约束：**密文包按 space 维度存一份**（而非按设备），`space_id` 主键——避免两份包不一致；任一方更新即覆盖，双方口令必须相同（或各自记住自己的口令，但包内容加密钥匙是同一口令派生）。

> **决策点（待审核）**：按 space 存一份（双方必须用同一口令）还是按设备存两份（各自口令）？推荐**按 space 一份**——语义简单，口令由老板告知朋友，天然一致。

### 4.3 与现有接口的关系

- 不修改任何消息/同步/附件接口；`seal`/`import` 流程**保留**作为无口令的离线兜底（不强制迁移）；
- `/key-escrow` 与现有备份/恢复（backup.dart）正交：备份是**文件级**全量，key-escrow 是**在线接入**辅助。

## 5. 新设备 / 朋友接入流程

```
朋友侧（新手机，仅需口令）：
① 设置页：服务器地址 + Space ID + 口令
② 客户端生成设备身份（公钥/私钥）
③ 白名单登记：公钥发给老板 → 老板加入 config.json 重启（现有流程，不变）
④ 认证通过（challenge-response，现有流程）→ GET /key-escrow 拉密文包
⑤ 输入口令 → 本地 Argon2id 派生 → 解出 Space Key → 进入聊天页
⑥ （可选）App 设置启动锁 PIN（现有功能）

老板侧：
① 设置页输入口令 → POST /key-escrow 上传密文包（一次性）
② 之后朋友/新设备按上述流程凭口令接入
```

**相比现状**：朋友不需要拿密钥信封文件、不需要理解"密封"概念——只需要知道一个口令。

## 6. 安全分析

### 威胁模型（目标：Server 与任何无口令者不可解密）

| 攻击场景 | 结果 |
| --- | --- |
| Server 被入侵 / 数据库与备份泄露 | 仅得密文包；无口令解不开（Argon2id + XChaCha20） |
| 运维人员读取数据库 | 同上 |
| 口令泄露（老板告知场景） | 知晓口令者可用任意设备接入——**口令即权限**，需谨慎保管 |
| 弱口令暴力破解 | 被 Argon2id 慢哈希 + 熵要求抑制；客户端本地错误锁定（可选） |
| 密文包被篡改 | AEAD tag 校验失败 → 解密报错，客户端提示重新拉取/重新上传 |
| 中间人（TLS 之外） | 传输已走 HTTPS；密钥包本身密文，即使剥离 TLS 也无意义 |

### 剩余风险

1. **口令即权限**：知道口令 = 可解出 Space Key。私用场景（老板 ↔ 朋友）可接受，但口令应区别于 App 锁 PIN；
2. **Server 依然可见元数据**：消息时间线、双方在线状态等（现有设计，不在本方案范围内）；
3. **口令丢失**：与恢复码机制互补——口令丢了可用 12 词恢复码（离线）兜底；两者都丢则数据不可恢复（与 E2EE 一致）。

## 7. 与现有机制的衔接

| 现有机制 | 关系 |
| --- | --- |
| App 启动锁 PIN | 独立：PIN 是"本地解锁"，口令是"接入/换机凭证"，互不替代 |
| 12 词恢复码 | 互补：恢复码是离线兜底（备份文件恢复），口令是在线接入（key-escrow） |
| seal/import 离线传递 | 保留为无口令兜底，不强制迁移 |
| 密钥轮换 rotate | 轮换后 Space Key 变更 → 需重新上传新密文包（客户端在 rotate 后自动 POST） |

## 9. 风险与权衡

| 项 | 权衡 |
| --- | --- |
| 便捷性 ↑ | 换设备/朋友接入从"传文件"变为"记口令" |
| 安全边界 | 从"物理传递密钥信封"变为"口令在信任圈内流通"——口令强度与保管成为新责任 |
| 兼容性 | 全兼容：无口令用户可继续 seal/import；两端流程并存 |
| Server 职责 | 从"哑转发器"变为"托管密文包"——仍是密文，职责扩展可控 |

## 10. 验收标准（建议）

- [ ] 无口令时 Server 数据全为密文（抽查 DB 无法还原 Space Key）
- [ ] 新设备凭口令完成接入（不触碰密钥信封文件）全流程走通
- [ ] 错误口令解密失败且不产生可用的部分密钥
- [ ] 篡改密文包 → 客户端报错不崩溃
- [ ] rotate 后自动重传密文包，朋友新设备拿到新密钥
- [ ] 撤销设备后其 token 无法再拉取密文包（复用现有白名单/会话机制）
- [ ] 既有功能回归：seal/import、收发消息、备份恢复全部不变

## 11. 待老板审核的决策点

1. **密文包按 space 存一份（双方同一口令）还是按设备存两份**？——推荐按 space 一份
2. **口令与 App 锁 PIN 是否强制区分**？——推荐区分（口令 = 接入凭证，PIN = 本地解锁）
